## 2. 执行原则

- 第一阶段把 MyGo 窗口与真实 Codex Runtime 连起来，尽早验证实际使用链路。
- 每次聚焦当前步骤，完成对应验收和问题修复后推进下一步。
- UI、应用状态、Codex 协议和进程管理保持清晰边界；引入第二种 Agent 时再根据实际差异提取 Adapter。
- 在实现过程持续维护 thread、turn、连接及待处理请求的独立状态，为后续恢复保留基础。
- 开发样例用于调试布局和异常状态；验收分别记录真实 Codex、协议夹具和 UI 样例的覆盖结果。
- 普通代码与文档修改保留在工作区；用户明确要求暂存时，仅暂存已核对且属于当前任务的文件。
- 参考下载文档保留作旧版对照，当前实施顺序以本文为准，技术约定以项目内设计文档为准。

## 7. 中断后如何接续

继续工作时按以下顺序执行：

1. 阅读本文“当前接续点”，确认已接受的方向、当前步骤和下一动作。
2. 核对工作区实际文件与已有修改；有 Git 仓库时检查分支和工作区/暂存状态。
3. 仅对当前步骤需要的环境重新核验版本、依赖和进程。将历史环境记录当作线索。
4. 阅读当前步骤涉及的设计约定和已有验证记录；仅在版本变化或存在新疑问时补充源码核验。
5. 从第一项未完成待办继续，保留已完成工作；完成必要验证后更新本文。

每次阶段完成或结束一轮开发前，更新“当前接续点”和当前待办，追加一条工作记录：

```text
日期与阶段：
本轮完成：
修改文件：
验证命令/操作：
结果与证据：通过 / 失败 / 未验证 / 暂缓；注明真实 Codex / 协议夹具 / UI 样例
剩余问题：
进程与环境：是否仍有任务、进程归属、临时目录和必要清理
下一动作：
```

实际运行任务时，将操作、关键结果和必要日志/截图记录到 `docs/verification/`，工作记录引用具体路径。仅在有实际证据时标记待办或阶段完成。长输出按需要保留摘要与脱敏证据。

如果发生意外中断且未来得及更新记录，接续时以实际文件、进程和可复核的运行结果重新确认进度。
